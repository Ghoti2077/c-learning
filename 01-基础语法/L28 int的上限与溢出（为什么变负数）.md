# L28 `int` 为什么有上限？太大为什么会变负数？

- 日期：2026-09-21
- 来源：**我自己问的**（做阶乘时 `13!` 输出怪值、`17!` 变成负数）
- 标签：`#C语言` `#基础语法` `#溢出` `#数据类型`

> **一句话总结**：
> **`int` 只有固定的 32 个格子（= 4 字节），能表示的个数是有限的**，所以有上限；
> 超过上限时不会报错，而是**"绕圈"窜到另一头去**（正数变成负数）—— 这叫**溢出**。
> 其中**最左边那一格被借去当正负号**，所以正数一半只能到 **2147483647**。

> [!warning] 待学（按我自己的要求）
> 这篇是**人话版**，够用来判断"会不会溢出"。**二进制补码的细节留到学「位运算」时讲**——那时候再回头看"为什么负数比正数多一个"。

## 1. 上限从哪来：格子数是固定的

```
sizeof(int) = 4 字节 = 32 位     ← 实测（1 字节 = 8 个 0/1 格子，32 个格子）
```

**打比方**：`int` 像一个**固定格数的里程表**。假如里程表只有 6 位数字：
它最多数到 `999999`，再往前走 1 格**不会变成 1000000**（没地方放），只会**翻回去**。

计算机里的数字也一样：**装不下的那一位直接丢掉**，结果就"绕"到别的地方去了。
**不同的地方**：里程表翻回 `000000`，而 `int` 翻到的是**负数那一头**（下面第 3 节解释）。

## 2. 为什么一半是负数：最左边那格是"符号位"

32 个格子里，**最左边那一个被借去表示正负**（约定 0 = 正、1 = 负）。
所以真正能用来表示"大小"的只剩 **31 个格子**：

| | 值 | 怎么来的 |
|---|---|---|
| 正数最大 | **2147483647** | 2³¹ − 1（31 个格子全 1） |
| 负数最小 | **−2147483648** | −2³¹（负数那半多占一个格子的名额） |

**实测**（`<limits.h>` 里的 `INT_MAX` / `INT_MIN`）：

```
INT_MAX = 2147483647
INT_MIN = -2147483648
```

**记法**：**2 的 31 次方 ≈ 21 亿** —— 以后看到"这个数会不会超过 21 亿"就能判断。
（`int` 只有 4 字节这件事，是 C 标准保证的"至少"，我们在 PC/单片机上都按 4 字节算。）

## 3. 太大为什么会变成负数：数轴其实是个"圈"

**把数轴弯成一个圈**：从 `-2147483648` 一路排到 `2147483647`，一共 **4294967296 个位置**，首尾相接。
走到最右边（2147483647）再往右走一格 → **绕到最左边**（-2147483648）。

**实测**：

```
INT_MAX        = 2147483647
INT_MAX + 1    = -2147483648   ← 越过上限，窜到负数区
INT_MAX + 2    = -2147483647
INT_MIN - 1    = 2147483647    ← 反向也一样：往另一边窜回正数
```

**注意**：整个过程**不报错、不警告、程序照跑** —— 只是**默默给出一个错值**。这比报错更危险。

## 4. 溢出到底"变成"什么：只留最低 32 位（实测闭环）

规则一句话：**结果只保留最低的 32 个格子（相当于对 4294967296 取余），再按"有符号"的方式读出来。**

这条规则**解释了我阶乘程序的所有怪值**（用 Python 独立算一遍对照，完全吻合）：

| 输入 | 真值 | 只留低 32 位 | 按有符号读 | 我的程序输出 |
|---|---|---|---|---|
| 12 | 479001600 | 479001600 | 479001600 | `479001600` ✅ |
| **13** | 6227020800 | 1932053504 | 1932053504 | `1932053504` ✅ 对上 |
| **17** | 355687428096000 | 4006445056 | **−288522240** | `-288522240` ✅ 对上 |
| **20** | 2432902008176640000 | 2192834560 | **−2102132736** | `-2102132736` ✅ 对上 |

→ **不是随机垃圾，是"按规则算出来的错值"** —— 能预测，所以也能防。

## 5. 那怎么办？几种正经对策

| 办法 | 说明 | 实测边界 |
|---|---|---|
| **换更大的类型** | `long long`（8 字节 = 64 位） | **能到 `20!`**：`20! = 2432902008176640000` ✅；**`21!` 就溢出了** → `-4249290049419214848` |
| **提前判断边界** | 算之前先问"加完会不会超上限" | 比如先比 `if (a > INT_MAX - b)` 再加 |
| **记常用上限** | `int`：±21 亿；`long long`：约 9.2×10¹⁸ | 看见数量级不对立刻警觉 |
| 换浮点/大数库 | 最后手段（浮点不精确，大数库要引入代码） | 以后按需 |

**阶乘这道题的结论**：

- `int` 装到 **12!**（479001600）
- `long long` 装到 **20!**（2432902008176640000）
- 再大就得用**大数算法**（数组存每一位，手写乘法）——那是"高精度"专题，以后再说

## 6. 这件事在嵌入式里更要命

- **8 位/16 位单片机上 `int` 可能只有 2 字节**（范围只有 ±32767）——**同一份代码在 PC 上跑得好好的，搬到板子上就溢出**。所以嵌入式里常写 `int32_t` / `uint16_t` 这种**明确位宽**的类型（`<stdint.h>`，以后学）。
- **溢出的场合经常是"关键控制量"**：PWM 占空比、电机转速、定时器计数值 —— 溢出成负数可能直接**反向驱动**，不是"算错个数"这么温柔。
- **主动利用溢出**：延时代码里用 `unsigned` 溢出做"无符号减法比较"是常见技巧（等学 `unsigned` 和位运算再回来）。
- **要报警的话得自己加**：硬件里没有"溢出异常"，靠程序员自己写检查。

## 7. 复习题（先自己答）

1. `int` 占几个字节、几个位？正数最大能到多少（大约多少亿）？
2. `INT_MAX + 1` 的结果是什么？为什么不是报错？
3. `int` 的 32 个格子里，最左边那一格被拿去干什么用了？这带来什么后果？
4. `int` 装不下的数，`long long` 能装到几的阶乘？再大怎么办？
5. 为什么说"溢出比报错更危险"？

> [!question]- 参考答案（先自己答完再点开）
>
> 1. **4 字节、32 位**；正数最大 **2147483647**（≈ **21 亿**，即 2³¹−1）。
> 2. 结果是 **−2147483648**（负数最小值）。因为计算机**不检查**容量：超出的那一位（第 32 位以上）**直接被丢掉**，剩下的 32 位按有符号读出来就成了负数 —— 数轴是个圈，越界就绕到另一头。
> 3. 被拿去当**正负号**（0 正 1 负）。后果：能表示大小的只剩 31 位 → 正数上限降到 21 亿；负数那边反而多一个名额（能到 −2147483648）。
> 4. **`long long` 能装到 `20!`**（2432902008176640000，实测），**`21!` 就溢出**。再大就得用**大数算法**（数组存各位数字，手写乘法）——"高精度"专题，以后学。
> 5. 因为溢出**不报错、不警告，程序照常跑完**，只是默默给出**错值**（比如 `17!` 变成 −288522240）。没有报错提醒你，只能靠自己算清"这个数最大能到多少"。在嵌入式里，错值可能直接驱动硬件动作。
