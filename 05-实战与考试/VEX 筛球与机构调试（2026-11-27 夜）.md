## 二、颜色筛选：三次推翻重来

### 第一版：`isNearObject()` —— 坏在不懂它的语义

```cpp
bool detect = sort.isNearObject();   // 全局！只算一次
```

两个病：

1. **`isNearObject()` 不是「看见球」**，是红外接近检测——比的是反射回来的红外强度有没有过阈值。传感器装在球道里、离黑壁几毫米，黑壁也照样超过阈值 → **恒为 true**（实测确认）。
2. **写在全局**，初始化在 `main` 之前跑一次就完事，之后永远停在开机那一瞬间的值。

> [!question]- 实测证据：全局 vs 现场问
> PC 上模拟（`scratch/detect_scope.cpp`）：全局 `detect` 四圈恒等于 1，而现场调用 `probe()` 每次 0/1 交替。
> ```cpp
> bool detect = probe();       // 全局，只算一次
> ...
> for(int i=0;i<4;i++){ bool now = probe(); ... }   // 现场问，每次都变
> ```

### 第二版：`sort.color()` —— 坏在它返回的不是 blue

实测：蓝球的 `color()` 是 `655355` = `0x09FFFB` = **RGB(9,255,251)，青色**；红球是 `16711680` = `0xFF0000`，纯红。

所以 `sort.color() == vex::color::blue` 永远 false。传感器的「蓝」和它自己那个常量对不上。

### 第三版（可用）：`hue` + 连续帧

实测数据——分得极干净：

| 状态 | hue | color 值 |
|---|---|---|
| 空载（黑壁） | **55** | — |
| 红球 | **17~20** | 16711680（纯红） |
| 蓝球 | **180** | 655355（青） |

```cpp
bool color_sort(){
    double hue = sort.hue();
    static int time = 0;
    static int blue_cnt = 0;

    bool is_blue = (hue >= 160 && hue <= 220);

    if(is_blue){
        blue_cnt++;
    } else {
        blue_cnt = 0;        // 只要一帧不是蓝，立刻清零
    }

    if(blue_cnt >= 4){       // 连续 4 帧(40ms)都蓝，才认
        time = 30;           // 球还在，继续刷 → 一直吐
        return false;
    }

    if(time > 0){            // 球走了，再吐 300ms 送它出门
        time--;
        return false;
    }

    return true;
}
```

> [!warning]- 这里踩过的两个坑
> **坑 1：一帧就刷 time。** 早期写的是「看到蓝就 `time=30`」，等于**单帧误判就吐 300ms**，红球被冤枉拨出去。连续帧判定才是解药。
> **坑 2：锁太长。** 曾用 `time=80`（800ms），蓝球 200ms 就送出去了，剩下的 600ms 里紧跟的红球全被吐掉 → 两球同时进来时红球白挨一顿。

## 三、机械：滚筒夹球原地转（高桥）

现象：球卡在中通道和上通道之间，左边一个滚筒右边一个滚筒，**球在中间逆时针自转**，不出门。

原因：两个滚筒的代码命令相同（都是 `reverse`），但机械上左右**镜像**安装，同一条命令到齿轮上变成物理上相反的方向 → 两个力构成力偶，球只转不走。

> [!tip]- 解法
> 一次翻一个（`intake2` 或 `intake3` 改 `fwd`），看球往哪走，两三次就能摸对。
> 代码本身没问题，是高桥的**结构**坏了——球走不出那条通道。

## 四、筛选轮 1% 微转（这一晚最精细的一手）

吸球那一支原来是 `sortmotor.stop()`，**橡胶静止时摩擦力最大**，红球被夹死过不去。改成：

```cpp
sortmotor.spin(fwd,1,pct);      // 只有 1%
```

为什么是 1%：刚好越过橡胶的**静止摩擦**，让红球滑得过去；但转速低到**抓不住蓝球**——蓝球进来时还是被 `reverse 100` 甩出去。调大（30/50/80）会把蓝球一起带上来。

> 静止摩擦 > 滑动摩擦，这是这一手的物理依据。

## 五、底盘漂移 = 手柄硬件

- 现象：只有 `Axis1` **向左轻推**、或者多次快速轻推才漂，别的方向都没事。
- 实测：松手时 `Axis1.position()` 停在 **-13 ~ -14**（假零点），死区 ±6 挡不住 → 车以为你在往左推 13%。
- 试过补偿零点（`+13`）——**不行**，因为零点会晃，补完往右漂。
- 结论：电位器磨穿了，代码治不了。**汇报学长**，考核任务不值得为坏手柄改代码。

## 六、代码层面踩到的三个坑（都能复用）

1. **全局变量初始化只跑一次**：`bool detect = sort.isNearObject();` 写在函数外，永远停在开机值。要用就现场问。
2. **一帧误判 + 长锁定 = 误伤后面的输入**：`time=80` 的教训。
3. **同一支里电机方向互相打架**：吐球时 `intake1` 还 `fwd` 往里送、`sortmotor` `reverse` 往外拨，球停中间。编译通过、看不出错，只有上机才现形。

> 这三条属于「编译通过 ≠ 对」系列，跟之前抓到的 PORT9 重复端口、`static bool now` 钩子不翻转是一类。
